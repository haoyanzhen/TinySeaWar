# Tiny Sea War 技术架构

> **功能与边界**：本文是项目技术路线、分层、依赖方向和运行时协作原则的权威来源。它回答“系统如何分层、状态如何流动、跨层依赖如何受控”。玩法规则见 `10–19`，数据字段见 `20–26`，当前代码位置见 `34_implementation_map.md`，完成状态只见 `00_project_status.md`。

## 1. 技术基线

- 引擎：Godot 4.x，主要使用 GDScript。
- 开发平台：macOS。
- 目标运行平台：Windows 11 与 macOS。
- 战斗模型：固定 Tick、命令驱动、事件输出；Domain 规则可脱离场景树运行。
- 配置模型：设计定义从 `data/` 加载，运行时状态由战斗会话创建，不回写定义对象。
- 表现模型：Presentation 消费快照与事件，不自行结算命中、伤害、侦查、装填或设施规则。

发布包必须验证启动、窗口与分辨率、鼠标输入、中文字体、用户目录读写和资源完整性。具体完成情况记录在 `00_project_status.md`，不在本文维护。

## 2. 分层与依赖方向

项目采用四层结构：

```text
Presentation  ──commands──>  Application  ──calls──>  Domain
      ^                          |                       |
      |                      snapshots/events           |
      +--------------------------+                       |
                                 v                       v
                         Infrastructure <── adapters/config/assets
```

依赖规则：

1. **Domain** 保存权威战斗状态并执行规则，不依赖场景树、HUD、贴图路径或输入设备。
2. **Application** 组织用例、战斗会话、固定 Tick、命令队列、AI 调度、快照与事件转发。
3. **Infrastructure** 负责配置加载、校验、资产目录、持久化、报告写出和引擎适配。
4. **Presentation** 负责输入翻译、节点生命周期、动画、VFX、音画反馈和 HUD。

允许外层依赖内层稳定接口；禁止 Domain 反向访问 Presentation 或 Infrastructure 的具体实现。跨层传递使用定义、命令、快照、事件和只读查询结果，不传递场景节点作为规则状态。

## 3. 各层职责

### 3.1 Domain

Domain 负责：

- 战斗实体、阵营、武器、技能、投射物和公共战斗时钟的运行时状态。
- 命令合法性、移动、侦查、装填、攻击、伤害、效果和胜负结算。
- 硬地形、环境和设施子域通过明确服务接口参与结算。
- 产生事实事件和可序列化快照。

核心战斗契约见 `32_domain_design_phase1.md`；硬地形见 `35_scene_combat_domain_design.md`；环境运行时见 `37_environment_runtime_domain_design.md`；设施见 `38_facility_combat_domain_design.md`。

### 3.2 Application

Application 负责：

- 创建、推进、暂停和结束战斗会话。
- 把玩家、AI、教学和设施操作转换为 Domain 命令。
- 在固定 Tick 边界排序和提交命令。
- 调用导航、目标、关卡、增援、模拟等应用服务。
- 对 Presentation 与测试输出过滤后的快照和事件。

Application 不拥有第二套战斗规则。需要裁决合法性时，应调用 Domain 服务并使用统一拒绝原因。

### 3.3 Infrastructure

Infrastructure 负责：

- 从 JSON、Resource 或用户目录加载定义与存档。
- 按 `20–26` 的契约完成类型、枚举、引用和跨文件校验。
- 通过语义资产目录解析表现资源，避免业务代码拼接物理路径。
- 为无图形模拟、报告、日志和测试提供文件系统与引擎适配。

加载器可以报告错误，但不能悄悄改变规则值。迁移或兼容逻辑必须显式、可测试、可移除。

### 3.4 Presentation

Presentation 负责：

- 将鼠标、键盘和 UI 操作翻译为应用命令。
- 根据阵营可见快照创建、更新和回收战场视图。
- 消费事件触发动画、投射物飞行、VFX、数字和 HUD 反馈。
- 在资源缺失时按稳定降级策略继续呈现。

表现架构见 `33_domain_design_phase2.md`，美术资产语义接口见 `45_art_asset_interface_design.md`。

## 4. 运行时拓扑

### 4.1 启动与注册表

启动阶段由注册表加载配置和资产元数据：

- `DataRegistry` 提供运行时定义入口。
- `ConfigRegistry` 执行配置装载、索引与校验。
- `AssetCatalog` 把稳定语义 ID 映射到具体资源。

注册表提供只读定义。单局战斗不得修改共享配置对象，也不得用表现资源是否存在推断规则是否可用。

### 4.2 游戏流与战斗会话

游戏流负责菜单、关卡选择、战斗创建、结算和返回。`BattleSession` 是单局应用协调器：

1. 接收关卡、舰队、种子与运行选项。
2. 从定义创建独立的 Domain 状态。
3. 收集玩家、AI 与脚本命令。
4. 按固定 Tick 推进 Domain。
5. 发布阵营可见快照、事件和结算结果。

同一进程内的多次实验必须隔离状态；模拟器不得复用上一局的可变对象、随机序列或事件队列。

### 4.3 快照与事件

- **快照**描述某一 Tick 后的可观察状态，适合 HUD、AI 和重建视图。
- **事件**描述已经发生的事实，适合一次性动画、音效、日志和统计。
- 表现层不得从事件反推完整权威状态，也不得把快照差异当成伤害结算。
- 隐藏信息在发布给消费者前过滤；AI 与玩家辅助只能访问所属阵营合法观察。

## 5. 固定 Tick、确定性与随机性

战斗规则只在固定 Tick 中改变。渲染帧可插值表现，但不得改变规则时间。

确定性要求：

- 初始定义、关卡、命令序列、Tick 步长和随机种子相同时，结果可复现。
- 随机抽取经会话持有的随机源完成，不使用渲染帧时间或全局隐式随机源。
- 同 Tick 命令、单位、武器和事件使用稳定排序键。
- 浮点比较使用统一容差和量化策略，避免由遍历顺序产生分歧。
- 日志至少携带实验 ID、运行 ID、种子、Tick 与规则版本标识。

无图形模拟的隔离、恢复与事实记录契约见 `19_battle_simulator_design.md`，实验清单字段见 `26_simulation_data_schema.md`。

## 6. 数据与运行时状态

数据分为三类：

1. **Definition**：加载后只读的角色、武器、技能、关卡、环境、设施、AI、表现和实验定义。
2. **Runtime State**：由一局战斗拥有的 HP、位置、冷却、弹药、状态、设施生命周期等可变事实。
3. **Derived View**：由定义与状态计算出的查询、快照、统计和表现参数。

不得在定义中保存单局状态，也不得在快照或 HUD 中保存权威规则状态。字段归属如下：

- `20_data_schema_design.md`：数据契约索引与公共加载原则。
- `21_combat_data_schema.md`：角色、武器、技能与核心战斗定义。
- `22_scene_environment_data_schema.md`：地形、环境与设施定义。
- `23_level_progress_data_schema.md`：关卡、目标与进度定义。
- `24_ai_data_schema.md`：AI 定义。
- `25_presentation_data_schema.md`：表现定义。
- `26_simulation_data_schema.md`：实验与模拟定义。

## 7. 子域协作

核心战斗 Domain 通过只读查询或显式命令与场景子域协作：

- 硬地形提供通行、碰撞、射线和空间语义查询。
- 环境提供单位位置与 Tick 对应的环境上下文。
- 设施提供归属、生命周期、任务和效果源查询。

子域不能直接修改核心状态的内部字段。移动、攻击、侦查和伤害服务消费其查询结果，再由权威结算写入状态。这样可以在开阔海域、岛屿、港湾和无图形模拟间复用同一规则链。

## 8. 导航与性能

导航分为低频战略走廊、常规动力学航迹和高威胁紧急避险；最终位移仍由 Domain 权威校验。正式预算与状态机分别见：

- `technical/t00_coastal_ai_performance_solution.md`
- `technical/t01_inertial_navigation_and_emergency_avoidance.md`

通用性能原则：

- 规则正确性与确定性优先于局部帧率优化。
- 对高频空间查询建立共享索引，不让每个系统重复扫描全场。
- 固定 Tick 中的昂贵工作使用显式预算、稳定队列和可观测指标。
- 缓存只能用于不改变语义的派生结果，并有清晰失效条件。
- 性能验收区分平均、P95/P99、峰值和退化路径，不用单次最快结果代替结论。

## 9. 持久化、版本与恢复

- 长线进度由 Application 发起、Infrastructure 写入，不由 Domain 直接访问用户目录。
- 存档包含 schema/version 标识；不兼容时应明确拒绝或迁移。
- 战斗中的检查点和实验恢复属于模拟平台，不等于玩家进度存档。
- 报告与日志是派生产物，不可反向成为运行时配置真源。

## 10. 资产与降级

规则定义只引用稳定表现 ID。资产解析失败时：

1. 记录可定位的缺失语义 ID。
2. 使用类别级或公共回退资源。
3. 若仍缺失，保留规则执行并使用最小可读占位表现。

资产缺失不得改变伤害、射程、碰撞或技能合法性。正式接口、目录与绑定点见 `45_art_asset_interface_design.md`。

## 11. 测试边界

- Domain 单元测试：规则、状态机、结算顺序、同 Tick 边界与确定性。
- Application 集成测试：命令编排、关卡目标、AI 观察隔离、快照和事件发布。
- Infrastructure 测试：数据校验、引用完整性、存档迁移和资产解析。
- Presentation 测试：视图生命周期、事件去重、隐藏信息与降级表现。
- Headless 回归：固定种子、多关卡、性能采样和报告一致性。

当前已有哪些测试、最近是否通过，只记录在 `00_project_status.md`。

## 12. 架构变更规则

架构性改动至少回答：

- 新状态由哪一层、哪个会话或子域拥有？
- 谁可以写入，谁只能查询？
- 输入以命令、定义还是查询进入？输出是状态、快照还是事件？
- 是否保持固定 Tick、确定性和隐藏信息边界？
- 数据字段、加载校验、测试和实现路引是否需要同步？

具体代码和数据位置始终以 `34_implementation_map.md` 为准，避免在本文形成第二份容易过期的目录清单。
