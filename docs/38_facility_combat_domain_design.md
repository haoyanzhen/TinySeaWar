# 设施战斗 Domain 设计

> **功能与边界**：本文定义岸炮、观察/雷达、补给维修、机场支援、水雷等设施的运行时状态、归属、任务、命令、事件和与核心战斗服务的协作。玩法效果与数值见 `18_facility_weather_effect_design.md`，字段契约见 `22_scene_environment_data_schema.md`，空间与环境查询分别见 `35/37`。

## 1. 设计目标

- 设施作为可观察、可争夺、可失效的 Domain 实体进入公共战斗规则。
- 玩家、AI、关卡脚本通过同一设施命令和合法性入口操作。
- 设施只提供任务、攻击或修正来源，不直接绕过侦查、攻击、伤害和资源规则。
- 五类主要运作模式共享生命周期、归属、快照、事件和拒绝契约。
- 具体数值与字段不在本文重复，避免和 `18/22` 形成双重真源。

## 2. FacilityState

每个设施运行时状态至少包含以下维度：

- 稳定设施 ID、Definition 引用和空间锚点引用。
- 当前阵营归属、可争夺语义和控制进度。
- 生命/耐久、启用、受损、瘫痪、摧毁等生命周期状态。
- 当前任务、任务阶段、目标、剩余时间与资源。
- 冷却、容量、补充或任务队列等类别状态。
- 观察权限、已发布事件序号和统计来源标识。

Definition 描述静态能力；FacilityState 描述本局事实。设施锚点由 `35` 提供，天气/潮汐条件由 `37` 提供。

## 3. 生命周期

### 3.1 通用阶段

设施至少区分：可用、执行任务、冷却/补充、受损不可用、摧毁。具体设施可扩展子阶段，但必须映射到这些公共可用性语义。

### 3.2 归属与争夺

- 归属改变只在固定 Tick 结算，并产生一次事实事件。
- 争夺合法性由距离、单位状态、敌我占领、设施状态和关卡规则共同决定。
- 归属改变时，旧阵营任务按类别契约取消、冻结或转移，不能静默继续服务旧阵营。
- 观察快照必须及时按新归属过滤设施信息。

### 3.3 受损、维修与摧毁

设施伤害使用公共攻击合法性、命中和伤害入口；设施 Definition 可以提供适用的碰撞与耐久语义。摧毁后不能启动新任务。维修只能由明确的设施或关卡规则恢复，表现动画不能改变生命周期。

## 4. 设施命令

设施命令由 Application 翻译后进入固定 Tick，至少覆盖：

- 请求控制/争夺设施。
- 启动、取消或切换设施任务。
- 指定合法目标、区域或受援单位。
- 请求补给、维修或其他交互。
- 布设、启停或管理允许控制的水雷区。

每条命令必须校验发布者权限、设施归属与状态、目标可见性、空间可达性、资源、冷却、环境条件和关卡限制。调试命令不进入正式战斗输入记录。

## 5. 五类运作模式

### 5.1 观测模式

观察站与雷达向 `ObservationService` 提供阵营级观测源：

- **观察站**使用其配置的观察语义参与公共侦查与视线规则。
- **雷达**是独立的 Radar 观测通道，按自身范围、目标类别、遮挡与反制语义参与查询；当前契约不把雷达降级为普通观察站，也不默认禁用。

设施只产生观测候选或修正来源，最终发现、残影和阵营共享仍由公共观察规则裁决。失效、易主或摧毁后必须撤销对应来源。

### 5.2 武器模式

岸炮等武器设施拥有目标选择、射界、装填、弹药和攻击状态。它们通过公共 Weapon/Damage 服务展开攻击：

- 不可攻击未满足其观察与目标合法性的单位。
- 不绕过地形遮挡、命中、装甲、伤害和事件链。
- AI 可请求目标或任务，但不能直接触发伤害。

### 5.3 服务模式

补给点与维修泊位处理对舰船的持续或阶段性交互：

- 受援单位必须满足阵营、位置、状态和设施容量条件。
- 服务期间的移动、受击、中断和并发规则由 Definition/玩法真源决定。
- 弹药、资源或 HP 的变化由一次可审计的服务结算产生。
- 同一 Tick 的多请求使用稳定顺序和容量仲裁。

### 5.4 支援任务模式

机场、通信站等设施可创建延迟完成的支援任务：

- 任务具有稳定 ID、发起阵营、目标、阶段、时限与取消原因。
- 目标合法性在提交和实际执行阶段按规则复核。
- 航空、侦察、火力或通信效果通过公共服务或状态效果入口结算。
- 设施易主、瘫痪、目标失效或环境不允许时按契约取消/失败。

任务表现可以预告或延后收尾，但不能改变权威执行 Tick。

### 5.5 水雷模式

水雷区由 `MinefieldState` 或等价子状态管理：

- 保存归属、布设/启用状态、剩余容量、已发现阵营与触发记录。
- 进入候选由 `35` 的空间查询提供，目标类别与敌我合法性由水雷规则判断。
- 触发后通过公共伤害入口产生事实，不能由表现碰撞直接扣血。
- 扫雷、禁用、重新布设和潮汐影响通过显式命令/环境上下文处理。

水雷发现信息按阵营过滤；不得因为水雷视图存在而向敌方泄露精确位置。

## 6. FacilityService 协作

FacilityService 在固定 Tick 中：

1. 接收并校验设施命令。
2. 推进归属、生命周期、冷却、容量和任务阶段。
3. 读取 `35` 的锚点/空间查询与 `37` 的环境上下文。
4. 向观察、武器、伤害、技能或运动服务提交明确来源。
5. 更新设施与水雷状态，产生事实事件。

FacilityService 不直接访问 HUD 或场景节点。核心服务通过设施 ID、来源 ID 和只读查询结果协作，避免彼此修改内部字段。

## 7. AI 与玩家共用边界

- 玩家设施操作来自 `11` 定义的交互状态，再翻译为设施命令。
- AI 只读取所属阵营可观察的设施状态，并按 `16` 的任务评分生成同类命令。
- 双方共享归属、距离、冷却、资源、目标合法性和中断规则。
- 玩家辅助模式不得把未发现设施/水雷信息交给自动控制。

## 8. 事件与拒绝原因

设施事实至少按类别覆盖：

- 归属开始变化、归属完成变化。
- 设施受损、瘫痪、恢复或摧毁。
- 任务接受、开始、完成、取消或失败。
- 岸炮攻击、服务结算、观测源启停。
- 水雷布设、发现、触发、禁用或耗尽。

稳定拒绝语义至少区分：权限/归属错误、设施不可用、目标不可见或非法、距离/空间不合法、资源不足、冷却中、容量已满、环境不允许、任务冲突和关卡禁止。表现文本由 UI 映射，不写进 Domain 事件。

## 9. 快照与观察权限

设施快照按阵营发布：

- 友方可见自身设施的任务、资源与冷却等允许信息。
- 敌方只看见已经发现且规则允许公开的类别、归属、受损和活动迹象。
- 水雷、隐藏任务目标和内部队列必须单独过滤。
- 调试/复盘全量快照使用独立权限，不复用局内接口。

设施事件也必须过滤；不能以一次岸炮或雷达事件泄露未发现设施的精确内部状态。

## 10. 确定性与不变量

- 同 Tick 多设施和多请求按设施 ID、任务优先级、发布者与序号稳定排序。
- 任务计时以规则 Tick 为准，不读取动画或墙钟时间。
- 概率性支援和水雷效果使用会话随机源。
- 一个任务只能进入一个终态；完成、取消和失败事件互斥。
- 摧毁设施不再产生新观测、攻击或服务来源。
- 归属、任务和效果来源在快照与事件中使用稳定 ID，可追溯到 Definition。

## 11. 校验与测试

加载时至少校验设施、任务、水雷、锚点、武器/技能和环境引用完整，类别与运作模式兼容。

运行时测试至少覆盖：

- 归属变化、受损、恢复、摧毁和任务中断的状态机。
- 观察站与独立 Radar 通道的启停、过滤和撤销。
- 岸炮使用公共目标、射界、地形和伤害链。
- 补给/维修的距离、容量、并发、中断与结算。
- 支援任务的提交、执行复核、取消和唯一终态。
- 水雷的布设、发现、触发、失效和阵营信息隔离。
- 玩家、AI 和脚本命令得到相同合法性结果。
- Headless 与带画面运行的设施事实一致。

当前实现与测试位置见 `34_implementation_map.md`，完成状态见 `00_project_status.md`。
