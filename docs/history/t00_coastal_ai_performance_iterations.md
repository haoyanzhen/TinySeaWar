## 13. 2026-07-02 实施与性能审计

### 13.1 本轮已实施

- `RoutePlanner` 在关卡加载时预构建 Profile、`nodes_by_id` 和节点空间网格，不再为每次路径请求重建全图节点字典；起终点连接只扫描附近网格单元。
- A* 开放集由每轮全量排序数组改为稳定同分规则的二叉最小堆，并加入 closed 集跳过重复展开。
- `TerrainQueryService` 在加载时预转换岸线/水域多边形，并为水域区域建立与岸线同级的空间网格；`regions_at` 不再遍历全部区域或逐次重建多边形。
- 潮汐通行由每 `4` 世界单位采样整段路线改为受控区域边界精确相交；仍允许单位从当前受限区退出，禁止从外部进入或穿越。
- 水雷区与安全航道多边形在加载时预转换；线段风险查询改为边界交点分段判定，不再固定步长扫描。
- AI 路线质量评分改为廉价直达/保守绕行估值；完整 A* 只保留在最终移动命令和中断恢复的权威路径阶段。
- 路线质量按单位、量化起点和量化终点缓存，失败结果使用较短 TTL。
- 设施与关卡任务结果按 `2.0s` 周期缓存复用；编组与阵列重建周期由 `5.0s` 调整为 `1.0s`，符合本方案 6.1 的当前设计值。

尚未实施：统一 `NavigationRequestBroker`、显式 revision 失效、完整路径请求硬预算/积压队列、编组主走廊共享、逐阶段 `AITraceProfiler`、11v11 有岸地图性能验收。因而本方案不能标记为完成。

- 关卡：`level.prototype_3v3` 与 `level.prototype_harbor_3v3`，均为 3v3。

- 计时：`/usr/bin/time -p`；相同比较使用各 `400` Tick，避免普通海域提前结算造成分母不同。

### 13.5 门槛判断与剩余热点

- **显著改善但未通过最终门槛**：港湾相对普通海域从至少约 `32.2x` 降至约 `4.11x`，仍高于本方案要求的平均 `3x`。
- 当前结果不能证明 P95 `<=4ms/Tick` 或 P99 `<=8ms/Tick`，因为逐阶段/逐 Tick profiler 尚未实施；只可确认平均墙钟成本。
- 完整 A* 和固定步长长线采样已不再是当前 3v3 的统治性热点。下一轮应先加入逐阶段计时，再审计港湾每 Tick的环境快照、设施/水雷深复制、地形移动合法性、视线查询和 AI 即时生存查询。
- 带画面战斗仍存在 `TerrainView` 每帧清空并重建环境区、设施和水雷节点的独立问题；本轮 headless 提升不代表渲染卡顿已经解决。
- 在 `NavigationRequestBroker`、revision、硬预算和有岸 11v11 验收完成前，状态继续保持“部分实施”。

## 14. 2026-07-11 新航迹规划搭配复验

### 14.1 方法与本轮调整

- 引擎为 Godot `4.6.3.stable.official`，headless Debug，固定 `0.1s` Tick；双方均启用当前完整运行时 AI。
- 对当前全部 `14` 个可运行关卡各执行固定种子 `20260711`、`400` Tick：`4` 个开阔规模关和 `10` 个近岸 3v3。此前另以三个相邻种子复测开阔与港湾热点，趋势一致；表中统一保留修改后的同种子全矩阵。
- `BattleSession` 新增可关闭的逐 Tick 微秒采样，只在显式性能测试时启用；分别记录整 Tick、AI 决策、常规/紧急航迹、移动，以及战略走廊、候选数和失败数。
- 本轮将 AI 初始决策与脏航迹重算按稳定实体槽位错峰；常规候选验证使用“战略走廊长程保证 + 候选中心线/终点快速拒绝 + 每 Tick 权威扫掠碰撞”，避免每个候选采样重复执行完整扫掠多边形查询。

### 14.3 门槛判断与风险

- **架构搭配成立，最终性能不合格。** 开阔 3v3 航迹 P95 为 `2.77ms`，表明短时动力学候选本身可控；但港湾平均 Tick 为开阔 3v3 的 `3.70x`，高于 `3x`，港湾 P99 为其 `21.6x`，远高于 `5x`。
- **最大风险已定位到同步战略路线。** 多张近岸图出现 `135 -> 242ms` 的 P99，个别 Tick 最大值更高；这些尖峰与低频完整走廊请求同 Tick执行相符。现有 `3/5s` 节流降低了频率，却没有限制一次 Tick 内的 A* 工作量，因此低频不等于预算有界。
- **大编队还有既有 AI 决策峰值。** 11v11 的 AI 决策 P95 为 `44.24ms`，高于航迹 P95 `8.68ms`；初始错峰只能削峰，目标/战术/编组及战略走廊仍需要统一预算队列和跨 Tick续算。
- **0.1s 扫描当前不是统治热点。** 每艘存活舰每 Tick只做轻量高威胁扫描，只有确认鱼雷或白名单高伤害攻击才进入紧急候选；本轮数据不支持为常规触岸风险启用紧急规划。
- 下一步继续完善 `NavigationRequestBroker`：紧急避险不入队，AI 战略走廊按稳定优先级实施可暂停的节点/微秒预算与过期取消，之后再进行有岸 11v11 合成压测与带画面验收。按当前决策不做请求合并和路线缓存。当前仓库没有有岸 5v5/11v11 关卡，因此本次全量测试只能覆盖现有十张有岸 3v3，不能据此宣称“有岸 11v11 已通过”。

### 14.4 首阶段统一请求入口

运行时已加入统一 `NavigationRequestBroker`，玩家和 AI 的战略走廊均先排队；每 Tick最多完成 `1` 条请求，玩家请求优先，同优先级保持提交顺序。请求不合并，也不使用成功或失败路线缓存。单位没有安全旧走廊时进入 `StrategicRouteWaiting` 并停车，有旧走廊时继续执行，完成后再原子替换走廊；沉没单位的排队请求会取消。紧急避险仍直接使用短时动力学候选，不进入战略队列。

复测中战略走廊单 Tick峰值已稳定为 `1`：开阔 11v11 的平均/P95/P99 从 `23.05/66.20/103.05ms` 降至 `18.28/42.81/57.33ms`。港湾 3v3 仍为 `13.14/17.85/177.40ms`，基本没有改善，证明剩余尖峰主要来自单条不可抢占路线调用，而不是多请求叠加。

因此当前只完成了“请求数量硬预算”，尚未完成严格的“微秒/节点扩展硬预算”。现有 A* 一旦开始仍需在当前 Tick返回；`2000us` 时间额度只能阻止开始下一条请求，不能中断当前请求。下一阶段必须把起终连接检查、A* 节点展开和路线平滑改为可暂停续算的工作单元，才能把单 Tick时间上限称为真正完成。按当前明确范围，不增加请求合并和路线缓存。

### 14.5 单条路线尖峰分解

对港湾、散布岛屿和环礁泻湖的单条请求进一步拆分计时。当前每个导航 Profile 约 `462 -> 540` 个节点，最慢样本的 A* 实际展开 `2 -> 210` 个节点；尖峰并不主要来自堆和节点展开，而来自 A* 前后的权威线段合法性查询。

| 代表样本 | 总耗时 | 起终接图 | A* / 展开数 | 平滑 | 主要占比 |
|---|---:|---:|---:|---:|---|
| 港湾最慢 | `256.08ms` | `103.76ms` | `36.42ms / 196` | `115.57ms` | 接图 `40.5%`，平滑 `45.1%` |
| 港湾低展开尖峰 | `196.80ms` | `148.61ms` | `8.64ms / 38` | `39.15ms` | 接图 `75.5%` |
| 散布岛屿最慢 | `219.43ms` | `197.58ms` | `0.13ms / 2` | `20.92ms` | 接图 `90.0%` |
| 散布岛屿长线 | `163.40ms` | `20.88ms` | `14.03ms / 132` | `127.39ms` | 平滑 `78.0%` |
| 环礁泻湖最慢 | `187.00ms` | `11.59ms` | `5.97ms / 60` | `168.74ms` | 平滑 `90.2%` |

根因是 `is_movement_segment_clear` 除岸线扫掠外，还通过 `_first_illegal_movement_fraction` 以约 `max(4, radius*0.25)` 的步长扫描整条线段，每个样点再次执行圆占位与区域多边形查询，遇到边界还会做 `16` 次二分。起终接图会对 `5x5` 空间单元内、距离 `420` 内的多个节点逐一执行该查询；当前平滑又从近到远测试全部剩余航点，长路线形成近似二次的重复长线扫描。

后续优化顺序应为：平滑改为从最远候选向近端搜索并命中即停；接图候选先按距离排序、找到 `8` 个可见节点后停止；静态水深/岸线边界使用烘焙 Profile 或空间索引下的精确边界相交，避免固定步长扫描。完成这些之后再判断是否需要优化 A* 本体；当前数据不支持优先重写堆或启发函数。

### 14.6 稀疏拓扑走廊实施与参数选择

战略层现改为只解决长期可达与拓扑进展：复用三档审核导航图，以中心线和距离做廉价候选预筛，A* 决定岛屿绕行侧和水道序列，再输出有半径的走廊门。烘焙边、直达段、最终采用的起终接入段和稀疏门间段统一用 `is_navigation_segment_clear` 做一次带 Profile 半径的连续校验：硬岸与地图边界使用扫掠，水域按区域边界交点分段并取最高优先级移动语义。战略层不对全部候选重复完整扫掠，不执行固定步长水深长线扫描、精确折线平滑或逐边水流收益积分；非法浅水目标投影到最近可达门。短时动力学航迹负责门间操舰和避岸，Domain 每 Tick仍执行权威扫掠碰撞。

参数扫描覆盖十张近岸图、双方完整 AI、每组 `120` Tick：接入候选 `4/6` 无明显功能收益差异；门间距 `160/180/200/220/240/320` 中，`160/180` 的岸线接触均为 `11` 次，`200` 为 `24` 次，`240` 为 `83` 次，`320` 为 `139` 次。最终选用门间距 `180`、接入候选上限 `4`，在保持较宽进度门的同时避免局部航迹跨过过长弯道。

最终参数对十张近岸图各执行 `400` Tick：总计 `4000` Tick，战略路线失败 `0`、动力学航迹失败 `0`、结束等待积压 `0`；九张地图岸线接触为 `0`，港湾为 `11` 次且均被权威碰撞阻止。平均每图 Tick耗时 `2.82ms`，最差地图 P99 `12.72ms`；相比旧精确战略路线的近岸 P99 `135 -> 242ms` 已消除主要尖峰。

单 A* 阶段测算显示：十图按地图平均的 A* 均值为 `2.23ms`，最大展开 `215` 个节点；九张非港湾图单次最大 `1.42 -> 4.10ms`，港湾最大 `13.81ms`。进一步分解发现旧 A* 最慢样本中约 `34 -> 36ms / 39 -> 40ms` 来自逐边完整环境上下文，尤其是重复计算水流和区域效果。移除不属于战略可达性的逐边水流/速度收益后，双水道礁线与长群岛最大 A* 从约 `38 -> 40ms` 降至约 `4ms`；港湾因仍需检查动态潮汐门保持约 `13.8ms`。因此剩余 A* 风险集中在港湾动态通行查询，而不是堆、启发函数或图规模。
